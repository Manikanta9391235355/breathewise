## Paste into Antigravity

Build and run Munim, a voice-first merchant assistant prototype for the Paytm Build for India AI Hackathon, Track 1 Merchant Growth AI. Ramesh runs a Hyderabad kirana and prefers spoken Telugu. He needs to hear what happened, understand what to do next, and approve any outbound action. Use the checked-in synthetic dataset and its expected_demo.json for acceptance checks. Inspect the repo first, keep compatible existing scaffolding, implement working code in it, and run the build and end-to-end smoke checks. Ask for a missing dependency only when it blocks a specific feature. Keep demo mode runnable with zero external keys.

### Stack and responsibilities

- React + Vite + TypeScript, responsive from 360px mobile to desktop. FastAPI + Pydantic for APIs and analytics. Use SQLite with a persistent local volume for the no-credentials demo. Use Supabase Postgres for deployment if a DATABASE_URL and connection work early. Share one repository contract and one migration/seed path per supported database. Serve built React and /api from the same HTTPS origin on the organizer's server where practical. Document local and hosted start commands and environment configuration.
- Use Python and SQL for metrics. JSON schemas and allowlisted intents cover daily_brief, sales_trend, product_growth, settlement_status, winback, and stock_planning. LLM can classify free-form requests or select an intent, language and date range. Validate its response. Calculate and speak all numeric facts from tools via localized templates. No generated SQL. Use deterministic multilingual shortcuts and quick actions if the provider fails or credits run out. Limit chat to one small request per uncached free-text question, set a timeout, and log call counts without storing transcripts or keys.
- Configure the organizer's actual chat, STT and TTS URLs, keys, model IDs and capability separately. Confirm from the handout whether the provider is Sarvam and what the 500 credits cover. Use Sarvam Saaras and Bulbul when provisioned and verified. Record on explicit tap using MediaRecorder, verify MIME support, send short clip to the backend, display an editable transcript and allow tap-to-play spoken responses. Support te-IN, hi-IN, en-IN. Show recording, processing, speaking and failure states. Test on the judging laptop and phone via HTTPS. If unavailable, use typed questions and localized one-tap prompts. Offer browser speech only when supported and clearly label any prerecorded demo example.

### Interface

Build a Paytm-inspired merchant home with original Munim identity and no official Paytm logo. Use a navy and cyan palette on a light background, clear ₹ values, high contrast, and visible focus states. Show a merchant switcher, demo data label, date selector, paid-sales summary, recent payments, settlements, and a prominent “Ask Munim” microphone and “Hear my summary” action. Keep the navigation consistent across mobile and desktop. On mobile use a compact bottom navigation and assistant sheet. On desktop use a left rail, main dashboard and assistant panel. Localize assistant controls, quick questions and actionable replies across Telugu, Hindi and English. Use large touch targets, full keyboard operation, clear mic status, and a transcript alongside audio. Keep charts light and add a text summary. Use progressive disclosure for products, expenses, suppliers, and import details.

### Data and API contracts

- Import the nine CSV tables under data/ in dependency order. Treat identifiers as strings, blank customer_id as anonymous, timestamps as ISO 8601, and amounts as integer paise. Scope all reads and writes by authorized merchant. Demo switching is allowed only in explicitly synthetic mode. If the public demo has no authentication, disable persistence of real uploads and external action adapters there. For real merchants require auth and tenant isolation with Postgres RLS where tables are exposed. Store keys server-side.
- Implement GET /api/health, GET /api/merchants, GET /api/dashboard?merchant_id=M01&from=YYYY-MM-DD&to=YYYY-MM-DD, POST /api/ask {merchant_id, locale, question, from?, to?}, POST /api/actions/preview, POST /api/actions/{id}/approve, POST /api/import/preview and POST /api/import/commit. An ask response includes intent, locale, spoken_text, typed facts, period, data_as_of, sources and optional preview reference. Freeze demo date at 2026-11-13 and use Asia/Kolkata for day boundaries. Live mode uses actual merchant-local time.
- Dashboard metrics include paid order count, paid sales, comparable date deltas, peak hour/day, item revenue and margin where costs exist, and pending versus overdue settlements. This dataset uses paid/failed/refunded as mutually exclusive terminal states and full refunds are excluded from paid sales. Item COGS comes from quantity × unit_cost_paise for paid sales. Gross profit is covered item revenue minus item COGS. Estimated operating result additionally subtracts recorded operating expenses, and needs a coverage label. Keep supplier bills and settlements in cash-flow views, with no double counting in profit. Payment-only events count in sales and coverage denominator, never in item totals or COGS. Show incomplete-cost coverage explicitly.
- Compare week or month like-for-like, rank product growth with a minimum baseline, and compare hourly patterns over adequate history. Flag unusual days against the previous four matching weekdays using a documented threshold and sample count. Surface the November sales surge and dip as observed patterns, with no causal claim. Show top selling categories, supplier bills due, and a stock-up scenario based on historical demand and known costs. Use a weekday baseline with a range if time permits. Pause forecasts when there is insufficient history. Use operating suggestions such as trialing a small reorder under a merchant-entered budget. Lending remains a simulated stock-up scenario with no eligibility prediction or application.
- For Excel/CSV import, prioritize the sample headers and then support explicit column mapping for merchant exports. Accept .xlsx and .csv, preview sheets/rows, validate money, currency, timestamps and foreign keys, flag duplicates, show row-level errors, and commit atomically. Use stable IDs or merchant-scoped external IDs for retries. Never evaluate workbook formulas or log customer details. Distinguish payment exports from POS orders, line items and supplier files. Do not link payments and inventory by amount alone.
- POST /api/demo/events accepts the attached simulated_event.json only in demo mode, with validation and a unique event key scoped to the merchant. Trigger from a simple “Simulate ₹125 payment” button. Use a brief poll/refetch or server-sent event to refresh the dashboard. Same event twice must only add one paid order. Show “Simulated live” as its source.
- Plug-in integration boundary for later. If official Paytm staging credentials and an enabled merchant API arrive, use a separate webhook adapter with signature validation, merchant mapping, event dedupe, and transaction status reconciliation. Follow that exact product's docs. Parse item data only from POS/Excel via explicit order ID joins. Existing QR merchant history, Soundbox, genuine outreach and lending need separate approved integration access.

### The signature flow

1. Ramesh taps the mic and asks “ఈ రోజు ఎంత అమ్మాం?” Munim reads the paid sales and order count and displays the same figures with the date.
2. Munim proactively shows one explanation or opportunity from the data. Example “Your 6–8 pm period is strong” only if true for the chosen range, or show the actual top period. On “ఎవరైనా రెగ్యులర్ కస్టమర్లు రావడం మానేశారా?” find customers with at least three distinct paid visit dates and last visit at least 15 days before the demo date. Filter for offer opt-in and exclude anonymous buyers.
3. Create a dated preview of a ₹20 offer with recipient count, maximum discount exposure, sample message and a visible approval control. Scope the approval to immutable stored preview and recipient IDs. Approve atomically and only once. Display a simulated outbox receipt and audit record. Show money recovered only from attributed sample redemptions, clearly marked simulated, if implemented.
4. Tap “Simulate ₹125 payment.” Paid count and revenue update without page reload. Play the refreshed brief from the same numbers. If time permits show the spreadsheet preview against one of the sample tables.
